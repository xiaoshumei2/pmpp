# 独立线程调度（Independent Thread Scheduling）与 SIMT 问答

---

# 问题一

> From the Volta architecture onwards, the passes may be executed concurrently, meaning that the execution of one pass may be interleaved with the execution of another pass. This feature is referred to independent thread scheduling.An important implication of independent thread scheduling is that one cannot assume that the threads of the warp reconverge after the divergent execution paths are exe- cuted.
> 详细解释下

先说这段话里的几个词：**pass** 是一个 warp 遇到分支分叉后，分别执行其中一条路径的那一轮。比如 `if/else` 里，执行 if 分支算一个 pass，执行 else 分支算另一个 pass，每个 pass 里只有走这条路径的线程是活跃的，其余线程被屏蔽。

## 一、Volta 之前：pass 一个接一个执行，最后一定汇合

之前的架构里，一个 warp 只有**一个**程序计数器（PC）和一个活跃掩码。遇到分叉时：

```
if (tid < 16) { A(); } else { B(); }
C();
```

执行顺序是：先跑 A（线程 0 到 15 活跃，16 到 31 被屏蔽），A 全部跑完，再跑 B（反过来），B 也全部跑完，然后到汇合点（`C()` 的位置）恢复成 32 个线程都活跃。硬件用一个栈记录汇合点在哪里。

这里有两个性质：
1. 一个 pass 要**完整**跑完才轮到另一个。
2. 分叉之后**一定**在汇合点重新汇合，所以 `C()` 里 32 个线程一定同步到达。

很多老代码依赖第二点，叫"warp 同步编程"：认为同一个 warp 里的线程在同一条语句上是锁步的，所以不写同步也安全。

## 二、Volta 起：每个线程有自己的 PC 和调用栈

独立线程调度把状态改成**每个线程**一份 PC 和调用栈。硬件仍然把"PC 相同的线程"打包成一次 SIMT 执行，但打包的方式变得灵活：

- 两个 pass **可以交错**：先执行 A 的前几条指令，切到 B 的几条，再切回 A……
- 分叉后线程**不保证**在汇合点重新汇合。调度器可能让它们汇合以提高效率，但这是它的优化选择，不是承诺。

## 三、"不能假设重新汇合"意味着什么

仍以上面的代码为例，在 `C()` 处，你不能假设线程 0 到 15 和 16 到 31 同时到达。典型的会出问题的代码是经典的 warp 内规约：

```cuda
// 依赖锁步，在 Volta 及之后可能出错
volatile float *s = shared;
if (tid < 32) {
    s[tid] += s[tid + 16];
    s[tid] += s[tid + 8];
    s[tid] += s[tid + 4];
    s[tid] += s[tid + 2];
    s[tid] += s[tid + 1];
}
```

这里每一行读到的 `s[tid + k]` 必须是上一行其他线程已经写好的值，原来靠锁步保证。独立调度下，线程 0 可能已经跑到下一行，而线程 16 还没写完上一行，结果读到旧值。

**修复**有两种：
1. 在每步之间加 `__syncwarp()`，让 warp 内参与的线程在这里汇合，并保证内存可见。
2. 直接用 warp 级原语，比如 `__shfl_down_sync(0xffffffff, val, offset)`。

## 四、为什么 NVIDIA 要这样改：为了避免死锁

在旧模型里，下面这种 warp 内自旋锁可能**死锁**：

```cuda
while (atomicCAS(&lock, 0, 1) != 0) { }   // 抢锁，抢不到就自旋
critical_section();
atomicExch(&lock, 0);                      // 释放
```

旧架构里，抢到锁的那个线程和自旋等锁的线程在同一个 warp，分叉后硬件可能一直执行自旋那个 pass，持有锁的线程所在的 pass 永远轮不到，释放不了锁，死锁。

独立线程调度保证**每个线程最终都会前进**（无饥饿），所以持锁线程总能轮到。这对在 GPU 上写细粒度同步的数据结构很重要，这也是它的主要动机之一。

## 五、几个容易误解的点

**1. "并发执行"不等于并行执行。**
一个子分区每个周期只发射一个 warp 的一条指令，所以两个 pass 是**交错**的，不是同时跑。分叉依然有性能代价：走不同路径的线程仍然不能在同一个周期里一起干活，活跃线程占比下降，吞吐下降。独立调度解决的是**正确性和进度保证**，不是消除分叉的开销。

**2. `__syncwarp(mask)` 和 `*_sync(mask, ...)` 里的 mask 是必须正确的。**
mask 告诉硬件"哪些线程要在这里汇合"。如果 mask 里的某个线程根本没走到这条语句（比如它在另一个分支里），行为未定义。所以带 `_sync` 的原语要求你写清楚参与的线程集合，不再允许像旧版 `__shfl` 那样默认整个 warp。

**3. 不依赖隐式 warp 同步，是写新代码的规则。**
只要写 warp 内通信，就用带 mask 的原语或 `__syncwarp()`，别指望编译器或硬件替你汇合。

**4. 有兼容模式。**
如果编译时用 `-arch=compute_60 -code=sm_70` 这类组合，Volta 及之后的 GPU 上会按旧的调度行为运行，可以让老代码暂时不出错，但这是权宜之计，我不建议依赖它，具体行为请查 CUDA 编译文档。

## 六、对应到你的学习

你读的 PMPP 规约章节里，较新的写法已经用 `__shfl_down_sync` 或 `__syncwarp()`，原因就在这里。你的 RTX 3050 是 sm_86，独立线程调度是默认开启的，所以你自己写 warp 内规约时，要把同步写出来。

**一个简单的验证实验**：写一个 warp 内规约的 kernel，一版用"锁步假设"的写法，一版加 `__syncwarp()`，在 sm_86 上跑大量次数，比较结果是否一致。注意错误版本不一定每次都出错，这类 bug 是**偶发**的，所以才危险。要稳定复现，可以用 `compute-sanitizer --tool racecheck` 去检测竞争。

# 问题二

> 这不是违反了同一时刻一个warp内的线程执行同一条指令吗

**不违反，因为"同一时刻执行同一条指令"一直只是对"当前这次发射里活跃的线程"说的，独立线程调度没有改变这一点。**

## 一次发射里仍然是同一条指令

调度器每个周期只为这个 warp 发射**一条**指令，这条指令对应**一个** PC。这次发射里，PC 等于这个值的线程是活跃的，一起执行；PC 不同的线程这个周期不执行，被屏蔽。

所以任何一个周期里，被执行的那些线程执行的都是同一条指令，这句话依然成立。

## 其实旧架构里这句话也不是对整个 warp 说的

即使在 Volta 之前，分叉时也是这样：if 分支的 pass 里，else 那一半线程被屏蔽，没有执行这条指令。所以"一个 warp 的 32 个线程同一时刻执行同一条指令"从来只是一个简化说法，准确的版本是"同一时刻执行的线程执行的是同一条指令"。

## 独立线程调度改变的是什么

它改变的是**调度器在不同 PC 的线程组之间怎么切换**：

| | Volta 之前 | Volta 及之后 |
|---|---|---|
| 每个周期发射 | 一条指令，给一组 PC 相同的线程 | 一条指令，给一组 PC 相同的线程 |
| 不同路径的线程组 | 必须一个跑完再跑另一个 | 可以交错：跑几条换一组 |
| 分叉后汇合 | 硬件保证在汇合点汇合 | 不保证，调度器可自行决定 |

用一个时间线看：

```
周期 1: 发射 A 的第 1 条指令  → 线程 0-15 执行，16-31 屏蔽
周期 2: 发射 B 的第 1 条指令  → 线程 16-31 执行，0-15 屏蔽
周期 3: 发射 A 的第 2 条指令  → 线程 0-15 执行
...
```

每个周期都符合"同一条指令"，只是相邻周期服务的线程组不同。这就是书里说的"一个 pass 的执行和另一个 pass 的执行交错"。

## 为什么这样仍然有用

关键是**两组线程在不同周期各自推进**，所以持锁线程所在的组总有机会被发射，不会被另一组一直占着。这解决的是进度保证和死锁，不是让两组在同一个周期并行。

## 一个需要保留的不确定点

"一个调度器每个周期只发射一个 warp 的一条指令"是我对 Volta 以后架构的理解。NVIDIA 没有公开所有微架构细节，所以"硬件内部是否在某些情况下能同时处理一个 warp 的两个不同 PC 的指令"我不能 100% 排除，但编程模型层面你按"一个周期一组 PC 相同的线程"来理解是安全的，也是文档给出的行为。

# 问题三

> 同一个path的线程永远都是执行同一条指令？不同path的线程不一定吗？

**不能这样说，因为决定能不能一起执行的是 PC，不是 path。**

## 1. 同一个 path 的线程，不一定永远在同一条指令上

- **Volta 之前**：同一个 path 里的活跃线程共用一个 PC，所以确实是锁步的。
- **Volta 及之后**：每个线程有自己的 PC。调度器会把 PC 相同的线程打包一起发射，但**不保证**一直打包在一起。即使它们走的是同一边分支，硬件也可以让其中一部分先走，另一部分后走。这正是文档说"不能假设线程重新汇合"的原因，哪怕你认为它们没有分叉过。

实际中，没有分叉过的线程通常是一起走的，但这是实现行为，不是编程模型保证，所以才需要 `__syncwarp()` 这类显式同步。

## 2. 不同 path 的线程，也可能在同一条指令上

path 只是描述"代码走哪一边"，真正的判据是**当前的 PC 是否相同**。不同 path 的线程可能碰巧到达同一条指令：

```cuda
if (tid < 16) { x = f(a); } else { x = f(b); }   // 两边都调用同一个函数 f
```

两边都会进入函数 `f` 的同一段代码。如果调度器让它们在同一时刻、同一个 PC，就能打包一起发射，这样反而更高效。这是独立线程调度允许的优化：它可以在分叉后的路径重新碰到同一段代码时，把线程重新聚到一起。

## 3. 总结成一个判据

| 情况 | 能在同一次发射里一起执行吗 |
|---|---|
| PC 相同 | **可以**，但硬件不保证一定打包 |
| PC 不同 | **不能**，必须分在不同周期发射 |

所以准确的说法是：**一次发射里一起执行的线程，一定是同一个 PC 的线程；反过来，同一个 PC 的线程不一定被同一次发射带走，同一个 path 的线程也不一定同一个 PC。**

## 4. 另一个容易混淆的点：同一条指令不等于同时完成

即使 32 个线程在同一个周期发射了同一条 load 指令，它们的**完成时间**也可能不同，比如有的命中缓存、有的要去 DRAM，或者地址分散导致被拆成多个事务。发射是同步的，完成不一定。这和上面讲的 PC 问题是两回事，但同样会让人误以为"一个 warp 内的线程总是同步的"。

# 问题四

> simt存在的意义是什么呢，这个不是违反simt了吗？所有线程都有独立的pc

**不违反。独立 PC 改变的是线程的"状态"，SIMT 的意义在于"执行"，两者不矛盾。**

## SIMT 存在的意义

GPU 的主要成本在**取指、译码、调度**这套前端，而不是算术单元本身。SIMT 让这一套前端被 32 个线程**共享**：发射一条指令，32 个通道一起算。这样同样的芯片面积和功耗里，可以放更多的计算通道，吞吐高很多。

同时，它让程序员**用标量方式写代码**：每个线程写自己的逻辑，包括 `if`、循环、不同的数据访问，不用像 CPU 的 SIMD 那样手动把数据打包成向量、处理边界和掩码。分叉由硬件负责，代价是性能下降，但**不会让程序出错**。

所以对比一下：

| | 写法 | 分叉 | 前端是否共享 |
|---|---|---|---|
| CPU SIMD | 显式向量 | 程序员用掩码处理 | 是 |
| **GPU SIMT** | 每个线程写标量代码 | 硬件处理 | 是 |
| 多核 MIMD | 每个核各自独立 | 不存在这个问题 | 否 |

## 独立 PC 为什么不违反

Volta 起每个线程**有自己的 PC 和调用栈**，这是线程的**逻辑状态**：它说的是"这个线程当前走到哪了"。但调度器**发射指令**时，仍然是找出 PC 相同的线程，打包成一组，一次发射给整组。

所以：
- **状态是独立的**：每个线程可以在不同的位置，这样才能保证"每个线程最终都会前进"（避免死锁、饥饿）。
- **执行仍然是共享的**：同一个 PC 的线程仍然被打包，共享一次取指、译码、发射。

SIMT 的核心是后者，也就是"一条指令对多个线程生效"，这一点没变。

## 如果所有线程完全各自独立会怎样

那就退化成 MIMD：每个线程自己取指、自己调度，前端成本乘以 32，就失去了 GPU 的面积和功耗优势。Volta 的做法是在**保留共享前端的前提下**，让线程在逻辑上更自由，并且让一个叫"汇合优化器"的单元尽量把 PC 相同的线程重新聚到一起，以保持效率。

## 一个更准确的理解

可以把 Volta 之前的模型理解成**"以 warp 为单位的 SIMT，分叉时线程被屏蔽"**，把 Volta 之后理解成**"以线程为单位的状态，加上以 PC 分组的 SIMT 执行"**。后者是前者的放宽，不是推翻。

你前面的追问其实触到了一个关键：教材里"warp 内的线程同时执行同一条指令"是一个简化说法，真正的保证是**"同一次发射里的线程执行同一条指令"**，而哪些线程被分在同一次发射里，是调度器的决定，不是编程模型的承诺。

# 问题五

> 假设没有control divergence，同一个warp内的线程是不是一定同步

**在实际硬件上基本是，但编程模型不保证，所以不能把它当作同步来用。**

## 实际硬件上通常是锁步的

没有分叉时，warp 内线程的 PC 相同，调度器会把它们打包成一次发射，一起执行同一条指令。这是硬件通常的行为。

## 为什么不能当作保证

**1. Volta 及之后，文档明确不保证。**
每个线程有独立的 PC，调度器可以选择不把它们一直打包在一起。没有分叉也一样，这是实现的自由度，不是你能依赖的行为。

**2. 编译器会重排指令。**
你以为线程 A 先写 `s[i]`，线程 B 再读 `s[i+1]`，但编译器可能把读写顺序改了，或者把值留在寄存器里不写回共享内存。这就是老代码里要加 `volatile` 的原因。即使硬件锁步，源码层面的"先后"也不保证。

**3. 内存可见性不等于同步。**
线程 A 写了共享内存，线程 B 什么时候**看得到**这个值，需要明确的同步或内存序保证。`__syncwarp()` 同时提供汇合和 warp 内的内存顺序保证，单纯"一起发射"不等于提供这个保证。

**4. "同时发射"不等于"同时完成"。**
前面说过，同一条 load 指令，不同线程完成时间可能不同。

**5. 隐式的分叉可能出现。**
"没有 control divergence"要看你有没有注意到所有的情况：数据相关的循环次数（每个线程循环次数不同）、提前 `return`、`break`，这些都是分叉，即使你没有写 `if/else`。

## 实用规则

只要代码**依赖**"warp 内线程在某处已经同步"这一前提，就显式写出来：
- 需要汇合：`__syncwarp(mask)`。
- 需要线程间交换寄存器：`__shfl_*_sync(mask, ...)`。
- 需要投票或归约：`__ballot_sync`、`__reduce_*_sync` 等。

这些原语带 mask，在 Volta 及之后都是正确的，也是官方推荐的写法。

## 一个类比

可以把"锁步"想成**当前硬件的一个实现细节**，类似于"这台电脑上 `int` 恰好是 32 位"。写能在以后的架构上继续正确运行的代码，要依赖文档承诺的东西，不要依赖"目前观察到的行为"。

# 问题六

> 前面说过，同一条 load 指令，不同线程完成时间可能不同。但是下一条指令的时候不用等上一条指令所有warp内线程执行完吗

**取决于下一条指令是否依赖这条 load 的结果。**

## 不依赖：不用等，直接发射

GPU 的 warp 是**按序发射**的，但 load 是**非阻塞**的：发射出去之后，warp 不会停在那里等数据。只要下一条指令不用这条 load 的结果，就可以马上发射。

```cuda
float a = x[i];     // load，发射后不等
float b = y[i];     // 另一条 load，也不等
int   k = i * 2;    // 不依赖 a、b，直接执行
float c = a + b;    // 依赖 a、b，到这里才需要等
```

编译器会特意把 load 往前排，让后面有足够多的独立指令可以填充等待的时间，这就是指令级并行（ILP）。

## 依赖：要等整个 warp 的 load 都完成

如果下一条指令用到了 load 的目标寄存器，它就要等。这里的等待是**以 warp 指令为单位**的，不是以线程为单位：

- 硬件用计分板（scoreboard）或依赖屏障，记录"这条 load 的目标寄存器还没写好"。
- 这条 load 在 warp 层面算完成，要等**全部**活跃线程的数据都回来。
- 有的线程命中缓存早就拿到了，有的线程还在等 DRAM，那么拿到数据的线程也要**等最慢的那个**，依赖指令才能发射。

所以我前面说的"不同线程完成时间可能不同"，是**硬件内部的**事实；而从 warp 和编程模型的角度看，一条 load 指令只有一个"完成"事件，就是最后一个线程的数据到齐的时刻。这也是为什么一个 warp 内的访存如果有一个"慢线程"（比如这个线程的地址没有合并、落在另一个缓存行或另一个 DRAM 页），整个 warp 都会被拖慢。

## store 的情况

store 通常是"发射后不管"：写请求发出去，warp 继续执行，不会等数据真正写进内存。这也是为什么需要 `__syncthreads()`、`__threadfence()` 这类东西来保证写入对其他线程**可见**。

## 对你的意义

这解释了两件事：
1. **隐藏延迟靠两个层面**：同一个 warp 里的独立指令（ILP），以及不同 warp 之间的切换（TLP，也就是 occupancy）。一个 warp 等依赖时，调度器去跑别的 warp。
2. **合并访问很重要**：不合并不仅让一次 load 变成多个内存事务，还因为 warp 要等最慢的线程，整个 warp 的依赖指令被推迟。

# 问题七

> divergence发生的时候就是各个线程pc不一样的时候

**基本上是，不过有几处细节需要补充。**

## 核心定义

**control divergence 就是同一个 warp 内的线程因为分支条件不同，走上了不同路径，导致它们的 PC 不一样。** 只要是同一个 warp 内的线程之间，PC 出现差异，就必须分多次发射，这就是分叉的代价。

## 几个容易混淆的情况

**1. 条件依赖数据，但 warp 内结果一致，不算分叉。**
```cuda
if (blockIdx.x % 2 == 0) { ... }   // 同一个 block 的线程结果相同
```
这个条件在 warp 内所有线程上算出来一样，大家走同一条路，PC 相同，没有分叉。反过来 `if (threadIdx.x % 2 == 0)` 同一个 warp 内结果不同，就有分叉。

**2. 不同 warp 之间走不同路径，不算分叉。**
不同 warp 本来就是各自独立调度的，各有各的 PC，互不影响。分叉只指**同一个 warp 内部**。所以把条件设计成"以 warp 为边界"（比如 `threadIdx.x / 32` 相关的条件），可以避免分叉。

**3. 编译器用谓词（predication）处理的短分支。**
很短的 `if` 编译器常常不生成跳转，而是让两边的指令都执行，用谓词决定结果是否写入。这时所有线程的 PC 其实是**一样的**，但一部分线程的执行结果被丢弃，同样浪费算力。所以"PC 不同"是分叉的典型表现，却不是浪费算力的唯一来源。

**4. 循环次数不同也是分叉。**
```cuda
for (int i = 0; i < n[tid]; i++) { ... }
```
每个线程的 `n[tid]` 不同，循环结束的时间不同，先结束的线程要等后面的，这也是 PC 不一致。

**5. PC 不同不一定是 control divergence。**
Volta 起每个线程有独立 PC，调度器可能在没有分叉的情况下让线程暂时处在不同位置（前面讲过，这是实现自由）。但这种差异不是由程序的控制流造成的，**不叫 control divergence**，也没有额外的性能代价设计进模型里。control divergence 特指**由程序的条件分支导致**的 PC 差异。

## 一句话总结

分叉 = 同一个 warp 内，因为数据相关的控制流，线程的 PC 出现了不同。性能上的代价来自"不同 PC 的线程不能在同一次发射里执行"，所以执行效率约等于 `活跃线程数 ÷ 32`。

# 问题八

> 最让我迷惑的就是volta之后的control divergence和simt的冲突，我感觉是矛盾的，前者给了线程独立调度的自由度，后者要求一个warp内的线程同一时刻执行同一条指令

你的矛盾来自两个说法被放在了同一个层面上，拆开之后其实不冲突。我先纠正一处：给线程"独立调度自由度"的是**独立线程调度**这个机制，control divergence 只是一种现象，Volta 之前就有。

## 矛盾出在对 SIMT 的理解

你把 SIMT 理解成了"一个 warp 内的 32 个线程**总是**同一时刻执行同一条指令"。这个理解一直是不准确的，在 Volta 之前，只要发生分叉，这句话就已经不成立：if 的 pass 里，一半线程根本没有在执行。

SIMT 真正的含义是：**每次发射一条指令，这条指令同时作用于一组线程**。它是对"一次发射"的描述，不是对"整个 warp 的所有线程在所有时刻"的描述。

## 独立调度到底给了什么自由

它给的**不是**"不同线程在同一时刻执行不同指令"，那样就变成 MIMD 了。它给的是调度器在**多组不同 PC 的线程**之间切换时的自由度。

两种模型的时间线对比，设线程 0 到 15 走 A 路径，16 到 31 走 B 路径，A、B 各有 3 条指令：

```
Volta 之前（每个周期都是一次发射，一组线程）：
周期 1: A1 → 线程 0-15
周期 2: A2 → 线程 0-15
周期 3: A3 → 线程 0-15
周期 4: B1 → 线程 16-31
周期 5: B2 → 线程 16-31
周期 6: B3 → 线程 16-31
周期 7: 汇合，C1 → 线程 0-31

Volta 之后（每个周期仍然是一次发射，一组线程）：
周期 1: A1 → 线程 0-15
周期 2: B1 → 线程 16-31
周期 3: A2 → 线程 0-15
周期 4: B2 → 线程 16-31
周期 5: A3 → 线程 0-15
周期 6: B3 → 线程 16-31
之后：调度器可以让它们汇合，也可以不汇合
```

**两种模型里，每个周期都满足"一次发射、一条指令、一组线程"**，SIMT 在这两个模型里都成立。区别只有两点：
1. A 和 B 可以交错，而不是一组必须完整跑完才轮到另一组。
2. 分叉之后，**不保证**在汇合点重新汇合。

## 为什么需要这点自由

唯一的价值是**保证每个线程最终都会前进**。回到自旋锁的例子：持锁的线程和等锁的线程在同一个 warp 里，如果必须一个 pass 完整跑完才轮到另一个，等锁的那组会一直占着发射槽自旋，持锁的那组永远轮不到，死锁。交错调度让持锁那组也能得到发射机会。

## 一个类比

把发射单元想成一位老师，32 个线程是 32 个学生，指令是"翻到第几页并做练习"。
- 同一页的学生，老师一次讲给他们听，这就是 SIMT。
- 学生翻到不同页，老师只能分别讲，这就是分叉。
- Volta 之前，老师必须讲完一页的全部内容，才能讲另一页。
- Volta 之后，老师可以今天讲 A 页第 1 题、B 页第 1 题、A 页第 2 题，轮流来；而且不强制要求大家最后回到同一页。

**老师仍然一次只讲一页**，这个没有变。

## 总结成一张表

| 层面 | 它回答的问题 | Volta 前 | Volta 后 |
|---|---|---|---|
| **执行（硬件）** | 一次发射给谁 | 一次一条指令，给一组同 PC 线程 | **相同** |
| **调度（顺序）** | 不同 PC 的组怎么排 | 一组完整跑完再换 | 可交错 |
| **汇合** | 分叉后是否一定汇合 | 保证汇合 | 不保证 |
| **线程状态（模型）** | PC 是共享的还是各自的 | 一个 warp 一个 PC 加掩码 | 每个线程各有 PC |

所以"每个线程有独立 PC"是状态层面的变化，"一次发射服务一组线程"是执行层面的不变量，两者不冲突。你一开始的疑惑很自然，因为教材通常只讲 SIMT 的简化版，Volta 的白皮书又直接讲"独立线程调度"，中间这层"状态和执行不是一回事"往往没有被说清楚。

# 问题九

> 周期 1: A1 → 线程 0-15 线程26-31也在执行和0-15相同的指令只是没有被激活

你这个看法在**硬件层面**是对的，我之前那样画容易让人误解。

## 硬件层面：指令发给整个 warp，掩码决定谁生效

一次发射的是**一条 warp 指令**，它被送到全部 32 个通道。同时有一个 32 位的**活跃掩码**，标明哪些线程这次真正生效：

```
周期 1: 发射 A1 → 32 个通道都收到
        掩码 = 0x0000FFFF
        线程 0-15 ：执行，结果写回寄存器 / 内存
        线程 16-31：被屏蔽，不写寄存器、不发内存请求、不产生副作用
```

从这个角度看，"一个 warp 内的线程同一时刻执行同一条指令"这句话是**字面成立**的，只是被屏蔽的那一半，它们的执行结果不起作用。分叉的代价也就很清楚了：**这些被屏蔽的通道在这个周期里空转，算力被浪费**，效率约等于 `活跃线程数 ÷ 32`。

## 线程层面：被屏蔽的线程并没有"执行"A1

如果从每个线程自己的状态看：线程 16 到 31 的 PC 此时在 B 路径上，它们的状态在周期 1 里**没有前进**。它们没有执行 A1，程序视角下 A1 与它们无关。

所以两种说法描述的是同一件事的两个层面：

| 层面 | 线程 16-31 在周期 1 里 |
|---|---|
| 硬件通道 | 收到了 A1，但被掩码屏蔽，不生效 |
| 线程自己的程序状态 | 没有执行 A1，PC 不变 |

## 我上一条里的时间线应该这样标

```
周期 1: A1 → 线程 0-15 生效（16-31 被屏蔽，通道空转）
周期 2: B1 → 线程 16-31 生效（0-15 被屏蔽，通道空转）
```

## 补充一个实现上的说明

被屏蔽的通道在物理上是否真的"空转"、功耗怎么处理，是实现细节，NVIDIA 没有公开。但对编程模型来说，只要记住两点就够了：被屏蔽的线程**没有任何可见效果**（不写寄存器、不访问内存、不触发异常），以及**这个周期的吞吐被浪费了**。

这也说明你前面一系列问题的出发点是对的：SIMT 在发射层面确实是"一条指令，整个 warp"，分叉时，不活跃的线程只是不生效，而不是真的在做别的事。

# 问题10
> 如果A只有A1，但是B有B1B2B3呢，走A那部分的线程执行完A了会怎样

取决于架构：Volta 之前，走 A 的线程会在汇合点等着；Volta 及之后，它们可以先往下走，也可以等，由调度器决定。

设代码是：

cuda
if (cond) { A1; } else { B1; B2; B3; }
C1; C2;
Volta 之前：A 线程等在汇合点
周期 1: A1  → 线程 0-15 生效（16-31 屏蔽）
周期 2: B1  → 线程 16-31 生效（0-15 屏蔽）
周期 3: B2  → 线程 16-31 生效
周期 4: B3  → 线程 16-31 生效
周期 5: C1  → 全部 32 个线程生效（已汇合）
周期 6: C2  → 全部 32 个线程生效

走 A 的线程在周期 1 做完 A1 后，周期 2 到 4 一直被屏蔽、闲着，直到 B 全部跑完，到汇合点，大家一起执行 C。总共 6 个周期。

Volta 及之后：有两种可能

情形一：调度器让它们先汇合（常见的、效率高的情况）
时间线和上面一样，6 个周期。

情形二：A 线程先往下走，不等 B

周期 1: A1  → 线程 0-15
周期 2: C1  → 线程 0-15（A 组先跑 C，16-31 此时还没到）
周期 3: C2  → 线程 0-15
周期 4: B1  → 线程 16-31
周期 5: B2  → 线程 16-31
周期 6: B3  → 线程 16-31
周期 7: C1  → 线程 16-31
周期 8: C2  → 线程 16-31

这时 C1、C2 被发射了两次，一次给 A 组，一次给 B 组，总共 8 个周期，比汇合后一起执行多了 2 个周期。分叉之后没有汇合，后面的代码也会一直被拆成两份来执行，直到它们重新碰到同一个 PC 并被打包。

所以独立调度允许情形二，但硬件有汇合优化器，会倾向于让线程尽快重新汇合以避免这种重复，实际上多数情况下你看到的是情形一。具体的启发式是 NVIDIA 没有公开的实现细节，我只能说"允许但倾向避免"。

对写代码的影响
不要假设走 A 的线程会等走 B 的线程。 如果后面的代码依赖 B 那一组已经算完的结果（比如读共享内存里 B 组写的值），需要显式 __syncwarp() 让大家汇合，否则 A 组可能已经读到了旧值。
A 很短、B 很长时，主要代价是 B 那段时间里 A 组的通道空转，这就是分叉的性能损失，两边越不平衡越浪费。
如果 A 里面有 return 或 break，那些线程直接退出了，后面的汇合只涉及还没退出的线程。
